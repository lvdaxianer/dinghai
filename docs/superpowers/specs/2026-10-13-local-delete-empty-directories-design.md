# Dinghai 本地文件删除空目录回收设计

## 背景

`LocalFileStorageAdapter.delete(ObjectKey)` 当前只删除对象文件和元数据，
对象所在的空目录会残留。当前仓库没有公共 `deletePrefix` 契约，因此本次只为
本地适配器增加本地专用的前缀删除能力，不改变 MinIO、RustFS、阿里云 OSS、
华为云 OBS 或公共 `FileStorage` 接口。

## 方案与取舍

### 方案 A：本地适配器内部完成删除和空目录回收（采用）

在 `LocalFileStorageAdapter` 中实现单对象删除后的父目录回收，并新增本地专用
`deletePrefix(String prefix)`。对象删除完成后，目录清理从最深路径开始，只用
`deleteIfExists` 删除空目录；目录不存在视为成功，非空目录停止向上清理。路径
解析复用 `LocalObjectPathResolver` 的 root 校验，并使用 `NOFOLLOW_LINKS`，避免
符号链接把删除操作引向 root 外部。

优点是影响面最小、远端实现完全不变，且能在本地模块内验证并发和安全边界。

### 方案 B：扩展公共 `FileStorage` 接口

为所有 provider 增加 `deletePrefix`。这会迫使对象存储实现定义不同的前缀删除
语义，扩大兼容面，并违反本次“只修改本地实现”的范围，不采用。

### 方案 C：由业务层执行目录清理

让业务侧执行 `rm -rf` 或自行遍历目录。该方案无法统一保证 root 边界、符号链接
安全、幂等和日志一致性，不采用。

## 设计

### 配置

新增 `dinghai.file-storage.local.cleanup-empty-directories`，默认 `true`。
该配置只绑定并传入 Local 适配器；关闭时仍删除对象文件和元数据，但不删除目录。
已有 Java 构造器保持默认开启，避免破坏直接实例化代码。

### 单对象删除

`delete(ObjectKey)` 保持既有返回语义：对象存在并删除成功返回 `true`，对象不存在
返回 `false`，删除 IO 失败抛出存储异常。元数据删除保持同一操作的一部分。文件
删除或元数据处理完成后，若开关开启，从对象父目录向 root 方向逐层尝试回收。
目录删除遇到并发不存在按成功处理；遇到非空目录停止；其他失败只记录 WARN，
不把已经完成的对象删除报告为失败。

### 前缀删除

`deletePrefix` 只接受规范化后的相对前缀，拒绝空前缀、绝对路径、`..`、反斜杠、
控制字符、root 外路径和指向符号链接的路径。扫描不跟随符号链接，只匹配 root
内的普通对象文件；每个对象同时删除元数据。对象删除失败会计数、记录安全日志，
继续处理其余对象，操作结束后以存储异常表示整体未完全成功。

对象处理完成后，目录按深度倒序尝试删除，root 本身永远不删除。目录非空、符号
链接或不在 root 内会被跳过；目录删除 IO 失败记录 WARN，但不影响已完成的对象
删除。多个任务同时删除同一前缀时，文件和目录的“不存在”结果均按幂等成功处理。

### 日志

前缀删除结束输出一条结构化汇总日志，包含 `prefix`、`deletedFiles`、
`deletedDirectories`、`skippedDirectories`、`failedDeletions` 和 `durationMs`。
失败日志不输出完整 root、密钥、元数据内容或用户文件内容；对象/目录标识采用
安全的相对标识或摘要，异常只记录类型和限长原因。

## 测试

本地模块测试覆盖：单对象空目录回收、多级前缀回收、非空父目录保护、重复删除、
中文及 URL 编码 key、路径穿越拒绝、符号链接保护、并发删除，以及关闭目录回收
开关后的行为。现有 MinIO、RustFS、OSS、OBS 测试继续运行，确认公共契约和远端
适配器不受影响。
